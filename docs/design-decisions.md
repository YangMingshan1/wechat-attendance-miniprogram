# 设计决策说明

> 本文记录系统设计过程中必须拍板的关键技术决策、备选方案与取舍理由。每一条都标注了**对业务规则的影响**，便于答辩时逐条说明。

---

## D1 · 设备 ID 的获取方案 ★ 最高风险项

**背景**：任务书要求"同一课程，同一个设备 ID 只能签到 1 次，无例外，靠小程序设备 ID 识别手机设备"。

**现实约束**：微信小程序**没有提供任何官方设备唯一标识 API**。`wx.getSystemInfo` / `wx.getDeviceInfo` 返回的 `brand`、`model`、`pixelRatio`、`screenWidth`、`platform` 等字段是**非唯一**的硬件与系统描述信息，同型号手机必然完全相同。因此"设备 ID"必须由开发者自行构造。

### 备选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（选用）** | 首次运行生成 UUID 存本地持久化缓存，登录时上报云端 | 稳定、无隐私争议、实现简单、**无误判** | 清除小程序数据或卸载重装后失效，可被主动绕过 |
| B | 拼接 `brand+model+platform+pixelRatio+screenWidth` 做哈希指纹 | 用户无感，重装后仍相同 | **同型号手机必然撞库**——全班使用同款机型时，第二个人起全部被误判为"已签到"而无法签到 |
| C | A + B 组合，A 作判定主键，B 作辅助审计字段 | 兼顾 | 判定规则需额外说明 |

### 决策与理由

**选用方案 A**，同时把方案 B 的指纹作为**辅助字段 `deviceFingerprint` 冗余记录**（仅用于管理员核对，不参与任何判定）。

核心权衡：**"可被绕过"与"误判正常用户"是两种性质不同的缺陷**。

- 方案 B 的撞库是**系统性误判**：只要班级里有两台同型号手机，就必然导致无辜学生无法签到，且管理员无法区分"他真签过了"和"他和别人手机型号相同"。这在签到场景下是致命的。
- 方案 A 的绕过是**主动作弊行为**：学生需要刻意清除小程序数据或重装微信小程序才能重置。这属于使用者的主观违规，而非系统缺陷。

因此选择"宁可被刻意绕过，也不误判正常用户"。

### 局限性的诚实声明（写入 README 与本文档）

方案 A 存在以下已知可绕过场景：

1. 删除小程序后重新进入 → 本地缓存被清除 → 生成新 UUID → 可再次签到
2. 在微信中"清除小程序缓存"
3. 使用多个微信号（本系统学生端不绑定 openid，此路径本身就不受设备约束）

**缓解措施**：

- 签到记录中**同时保存 `deviceFingerprint`**，管理员在记录列表中可直观发现"同一指纹 + 不同设备 ID"的异常组合，人工识别规避行为；
- 数据库层用**唯一索引**做兜底（见 D7），保证即使在并发场景下也不可能写入两条相同 `courseId + deviceId` 的记录。

> 若后续需要更强约束，可在不改变表结构的前提下追加方案 B 作为拒绝条件（`deviceFingerprint` 字段已预留），这属于策略调整而非重新设计。

## D2 · 签到距离在云端计算，不在客户端计算

**决策**：小程序端只负责调用微信原生定位 API 取经纬度并**原样上报**；是否在允许范围内，完全由云函数 `signIn` 使用 Haversine 公式计算并裁决。

**理由**：

1. 客户端计算的距离属于**不可信输入**。若在小程序端判定后再把结果上报，攻击者可通过调试工具直接调用云函数、或篡改返回值绕过距离限制。
2. 课程点位与阈值仅存在于云端数据库，小程序端**不下发**阈值参与前端判定，避免逆向推导。
3. 距离结果由云端回写入库，保证签到记录中的 `distance` 字段可信、可用于事后复核。

**附带校验**（云端）：经纬度必须为合法数值、`latitude ∈ [-90, 90]`、`longitude ∈ [-180, 180]`，否则直接拒绝。

## D3 · 数据库权限：关闭客户端直连，全部走云函数

**问题**：微信云开发数据库默认权限为"仅创建者可读写"。本系统需要**管理员读写全部数据**（跨用户查看签到记录），而学生**不绑定 openid**，用默认权限模型无法满足。

**决策**：

1. 所有集合权限统一设置为**「所有用户不可读写」**（即仅管理端/云函数可读写）：

   ```json
   { "read": false, "write": false }
   ```

2. 小程序端**不出现**任何 `wx.cloud.database()` 业务读写调用，所有数据操作一律通过 `wx.cloud.callFunction` 完成。
3. 云函数中使用 `cloud.database()`，拥有完整读写权限。

**收益**：数据可信性完全由服务端保证，"同课程同设备仅 1 次""超范围禁止签到"等规则无法从客户端绕过。

**代价**：所有查询需要走云函数，列表必须自己做分页（云函数中单次 `get()` 上限 100 条）。

## D4 · 管理员身份与首个管理员的产生方式

管理员的身份标识使用微信 `openid`（由云函数从调用上下文中获取，客户端**无法伪造**）。

**首个管理员**：通过**云函数环境变量 `ADMIN_OPENIDS`** 注入（值为 openid，多个用英文逗号分隔）。部署者在微信开发者工具中调用一次 `login` 云函数即可从返回的 `debugOpenid` 字段读到自己的 openid（该字段仅在非生产环境返回）。

**鉴权流程**：

1. 管理员在小程序内点击微信授权登录 → 云函数 `login` 拿到调用者 `openid`；
2. 若 `openid` 在环境变量白名单中 → 写库到 `admins` 集合（首次）并放行；
3. 若 `openid` 已在 `admins` 集合中 → 直接放行；
4. 否则返回 `NOT_ADMIN`，小程序提示"当前微信账号不是管理员"。

**理由**：避免"第一个管理员如何注册"的鸡生蛋问题；环境变量属于部署者私有配置，学生的微信账号无论如何都无法成为管理员。同时 `admins` 集合支持后续追加授权管理员，无需改代码。

## D5 · Excel 导入导出的实现路径

云函数运行在 Node.js 环境，使用 `xlsx`（SheetJS）依赖完成解析与生成。

**导入路径**：

```
管理员选择文件 (wx.chooseMessageFile)
  → 上传云存储 (wx.cloud.uploadFile)
  → 调用 student 云函数 action=import，传入 fileID
  → 云函数下载文件、解析、逐行校验
  → 批量写入 users 集合
  → 返回 { total, success, failed, errors: [{row, reason}] }
```

**逐行校验规则**：班级/姓名/学号三者任一为空 → 记为失败；学号格式非法或已存在 → 记为失败；同一文件内学号重复 → 保留首行、其余记为失败。**校验失败不影响其余行写入**，并返回明细供管理员核对。

**导出路径**：

```
管理员点击导出
  → 调用 export 云函数
  → 云函数查询记录、xlsx 生成 buffer、上传云存储
  → 返回 fileID
  → 小程序端 wx.cloud.downloadFile → wx.openDocument 预览/转发/保存
```

**分批写入**：导入时每批最多 100 条，避免单次写入超时与超出云函数限制。

## D6 · 云函数按业务域拆分（而非按接口拆分）

**决策**：拆分为 6 个云函数，每个函数内部以 `event.action` 分发子动作。公共代码（返回体、鉴权、距离计算、分页）抽到共享目录。

| 云函数 | 负责的动作 | 调用者 |
|---|---|---|
| `login` | `adminLogin`、`studentLogin` | 管理员 / 学生 |
| `course` | `list`、`create`、`update`、`remove` | 管理员 |
| `student` | `list`、`import`、`remove` | 管理员 |
| `record` | `list`、`update`、`remove` | 管理员 |
| `signIn` | 签到（单一动作） | 学生 |
| `export` | 导出签到记录 | 管理员 |

**理由**：微信云开发每个云函数都需要单独安装依赖、单独部署。若按接口拆成十几个函数，`xlsx` 这类依赖会被重复打包，部署与维护成本成倍增加。按域拆分在"部署次数"与"函数职责"之间取得平衡。

`signIn` 保持单一动作，因为它是**唯一允许学生角色调用**的函数，职责越窄越容易做安全审计。

## D7 · 去重采用"应用层校验 + 数据库唯一索引"双重保障

**业务规则原文**："同一课程，同一个设备 ID 只能签到 1 次，**无例外**"。

**决策**：在 `records` 集合上建立**复合唯一索引**：

```
courseId (asc) + deviceId (asc)   unique: true
```

签到时的执行顺序：

1. 云函数查询 `records` 中是否已存在 `{courseId, deviceId}` → 存在则返回 `ALREADY_SIGNED`（这是**快路径**，用于给出友好提示）；
2. 不存在则执行插入；
3. 若插入时被数据库唯一索引拒绝（捕获重复键错误）→ 同样返回 `ALREADY_SIGNED`。

**为什么必须加第 3 步**：仅靠"先查后写"存在经典的**竞态条件**。当同一设备的两次请求并发到达时，两次查询可能**都**返回"未签到"，于是两条记录都被写入，规则被破坏。数据库唯一索引是并发安全的最后一道防线，这才是"无例外"的真正兑现点。因此该索引**不是性能优化，而是业务约束的实现载体**。

## D8 · 学生与课程的关联方式

**问题**：学生名单由 Excel 批量导入，导入时不含课程信息；而签到是按课程进行的。二者之间没有直接的所属关系表。

**决策**：采用**开放式签到**模型——学生登录后**选择要签到的课程**（列表来自 `courses` 集合），而非先选课程再选学生。

**理由**：

1. 若要求"课程-学生"绑定，就必须再建一张关系表并做批量选课配置，而任务书**并未要求任何选课/排课功能**；
2. 任务书要求学生"输入学号 + 姓名，和后台导入学生名单匹配即可登录"——即**身份校验依赖全量学生名单**，与课程无关；
3. 任务书未要求"只有选了课的学生才能签到"，额外增加该限制属于**超出需求范围**。

**可选加固**：若部署场景确实需要限制签到范围（例如名单区分不同班级），可在 `signIn` 中追加一条判定"该学生是否在目标课程的允许名单内"，这不改变任何表结构，仅需为 `courses` 增加一个 `allowClassNames` 数组字段。**本项目默认不启用**，以严格贴合任务书需求边界。

## D9 · 签到无时间段控制的具体含义

任务书明确"不设置签到起止时间，不区分迟到、缺勤状态"。因此：

- `courses` 集合中**不设计** `startTime` / `endTime` 字段，从数据结构上就不存在时间段概念；
- `signIn` 中**不包含**任何时间比较逻辑；
- 签到记录只有 `signTime`（签到发生的那一刻），它用于**记录与导出**，**不参与任何准入判定**；
- 不存在 `status`（正常/迟到/缺勤）一类字段，因此系统在结构上无法产生迟到缺勤标记。

## D10 · 为何保留 `operator` / `updateTime` 字段而不算"操作日志"

任务书边界约束中有"不记录操作异常日志"。需要区分两个概念：

- **操作日志系统**：独立的数据表/集合，记录"谁在什么时间做了什么操作"，用于审计与追溯，通常包含登录、查看、失败等全量行为。
- **记录字段**：`records` 上附带的 `operator`（最后修改人 openid）与 `updateTime`（最后修改时间）是**业务数据自身的一部分**，用于说明"这条签到记录被谁改过"，属于数据完整性所需。

本系统**不建立任何独立的日志集合**，不记录登录行为、不记录查看行为、不记录失败尝试、不做异常上报。仅保留记录行上的必要溯源字段。这与边界约束不冲突。
